# Editar y borrar una sesión individual

**Estado: aprobada**

## Contexto y objetivo

La aplicación debe permitir corregir o eliminar una única sesión sin perder datos, sin usar el backup como fuente alternativa y actualizando únicamente el estado confirmado. La spec 006 amplía y, para sesiones, sustituye las reglas de alcance y validación de la spec 003: `version: 1`, raíz, objetivo, metadata y contadores siguen siendo compatibles, pero desde su activación las sesiones normalizadas incluyen `id` y pueden editarse o borrarse. La spec 003 sigue rigiendo backup, fechas y estadísticas salvo lo explícitamente modificado aquí. Para sesiones, 006 sustituye también el desempate final de 005: fecha descendente, `creado` válido descendente, `id` descendente e índice estable. README debe documentar las acciones. La aprobación es independiente del plan y las tareas; README puede leerse durante todo el flujo, pero solo se modifica o revisa públicamente en T10, tras la implementación y verificación.

## Historias de usuario

- Como estudiante, quiero editar una sesión concreta sin volver a registrarla.
- Como estudiante, quiero borrar solo la sesión elegida con confirmación irreversible.
- Como usuario de teclado o lector de pantalla, quiero operar cada sesión sin perder el foco.

## Requisitos funcionales

### RF-1. Identificación, compatibilidad y normalización

- **Criterio EARS:** En toda clasificación y normalización de documentos, el servidor/repositorio será la única autoridad: solo él decidirá entre `NORMALIZABLE` y `DATA_CORRUPT` y aplicará la normalización. El cliente nunca validará ni normalizará documentos completos ni asignará IDs; únicamente validará los campos de sus formularios y mostrará las respuestas recibidas.
- **Criterio EARS:** Cuando un documento haya sido normalizado, su contrato único de sesión normalizada será un objeto con `id` entero seguro positivo obligatorio, `fecha` texto `AAAA-MM-DD` de fecha real de calendario, `tema` string no vacío tras `trim`, `minutos` entero seguro positivo y `creado` opcional: si falta se conserva la ausencia y, si existe como entero seguro positivo, se conserva exactamente; si existe con cualquier otro valor, la normalización lo elimina por ser un campo conocido derivado opcional. `creado` nunca se inventa ni se transforma. Los restantes campos desconocidos se conservarán. La metadata normalizada contendrá obligatoriamente `migration` válida, `successfulWrites` entero seguro no negativo, `backupSuccessfulWrites` entero seguro no negativo y `nextSessionId` entero seguro positivo estrictamente mayor que todo `id`; los campos desconocidos se conservarán.
- **Criterio EARS:** Cuando se lea un documento cuya raíz sea un objeto y que tenga todos los campos obligatorios `version`, `sesiones`, `objetivoSemanal` y `metadata`, debe clasificarse como `NORMALIZABLE` si `version` es exactamente `1`, `sesiones` es un array, `objetivoSemanal` es `null` o un entero seguro entre `1` y `5040`, `metadata` es un objeto con `migration` estructuralmente válida y `successfulWrites` y `backupSuccessfulWrites` son enteros seguros no negativos, y cada sesión tiene fecha válida, `tema` string no vacío tras `trim` y `minutos` entero seguro positivo. En esa clasificación pueden faltar `id` y `nextSessionId`, o ser inválidos o estar duplicados, porque se reparan sin descartar sesiones.
- **Criterio EARS:** Cuando `metadata.migration` esté presente, solo será estructuralmente válida si es un objeto con `status` exactamente `pending`, `failed` o `completed`, `sources` un array sin duplicados de strings del inventario autorizado explícito (`diario-de-estudio-sesiones`, `diario-estudio-sesiones`, `diario-de-estudio-objetivo-semanal`), `ignoredSources` un array de objetos que contengan obligatoriamente `source` string autorizado, `reason` string y `count` entero seguro no negativo, y `completedAt` `null` o un texto con formato `AAAA-MM-DD`. `sources` e `ignoredSources` pueden coexistir, pero no pueden repetir un mismo `source`; los campos desconocidos adicionales de cada elemento de `ignoredSources` se conservan y se ignoran semánticamente. Esta spec no modifica ni procesa `sources` o `ignoredSources`: la migración histórica pertenece a la spec 003. Una fuente no autorizada en un documento existente produce `DATA_CORRUPT` conforme a spec 003 y no se añade a `ignoredSources`.
- **Criterio EARS:** Cuando `metadata.migration.status` sea `pending` o `failed`, `completedAt` debe ser exactamente `null`; cuando sea `completed`, `completedAt` debe ser un texto válido con formato `AAAA-MM-DD`; cualquier otra combinación es incoherente y debe clasificarse como `DATA_CORRUPT`.
- **Criterio EARS:** Cuando `metadata.migration.status` sea `completed`, no debe volver a procesarse ninguna migración.
- **Criterio EARS:** La normalización de esta spec no leerá `localStorage`, ni procesará, reintentará o modificará `migration.sources` o `migration.ignoredSources`, ni cambiará `migration.status` o `migration.completedAt`; únicamente validará y conservará ese objeto. La migración histórica es responsabilidad exclusiva de la spec 003.
- **Criterio EARS:** Cuando falte cualquiera de los campos obligatorios de la raíz (`version`, `sesiones`, `objetivoSemanal` o `metadata`), la raíz no sea un objeto, `version` no sea `1`, `sesiones` no sea un array, `objetivoSemanal` tenga un tipo o rango distinto de `null` o entero seguro `1..5040`, `metadata` no sea un objeto, `migration` no sea estructuralmente válida, `successfulWrites` o `backupSuccessfulWrites` no sean enteros seguros no negativos, o una sesión tenga inválida, ausente o mal tipada cualquiera de sus campos obligatorios (fecha válida, `tema` string no vacío tras `trim` o `minutos` entero seguro positivo), el documento debe clasificarse como `DATA_CORRUPT` y no normalizarse. Los valores inválidos de una sesión entrante en edit/delete producen `INVALID_SESSION_DATA`; la forma, tipos, campos ausentes o campos extra de la operación producen `INVALID_SESSION_OPERATION`.
- **Criterio EARS:** Cuando se clasifique el documento, los campos desconocidos adicionales de la raíz, `metadata` y las sesiones nunca deben invalidarlo por sí mismos, repararse ni eliminarse; deben conservarse estructuralmente. Solo `id` de sesión y `metadata.nextSessionId` tienen reparación permitida.
- **Criterio EARS:** Cuando un elemento de `sesiones` no sea un objeto, o cuando `sesiones` no sea un array, el documento debe clasificarse como `DATA_CORRUPT`.
- **Criterio EARS:** Cuando `successfulWrites` o `backupSuccessfulWrites` no sea un entero seguro no negativo, o cuando `backupSuccessfulWrites` sea mayor que `successfulWrites`, el documento debe clasificarse como `DATA_CORRUPT`; la igualdad y el valor menor de `backupSuccessfulWrites` son válidos.
- **Criterio EARS:** Cuando concurran campos obligatorios válidos con `id` ausente, inválido o duplicado, o con `nextSessionId` ausente o inválido, debe prevalecer `NORMALIZABLE`; la excepción de conservar un ID inválido solo aplica al documento legado antes de normalización. Después de normalizar, todos los IDs son enteros seguros positivos únicos y cualquier principal no normalizado debe rechazarse. Cuando falle cualquier requisito obligatorio de forma, tipo, rango o valor, debe prevalecer `DATA_CORRUPT`, aunque los identificadores sean reparables.
- **Criterio EARS:** Cuando se vaya a editar o borrar, el servidor/repositorio debe normalizar internamente el documento antes de aceptar y ejecutar la operación; si esa normalización falla, la operación no se ejecuta y responde `DATA_CORRUPT` o `WRITE_FAILED` según la matriz de persistencia. El cliente no valida el documento completo, no normaliza ni asigna IDs: tras HTTP 200 solo aplica el guard mínimo de transporte/render `result.document` objeto, `result.document.sesiones` array y `result.document.metadata` objeto; si falla, aplica `SESSION_INTEGRITY_ERROR` y ejecuta `GET /api/data`. Mientras la operación esté pendiente de un error conocido, las acciones permanecen bloqueadas; tras recargar puede reintentarse una nueva solicitud.
- **Criterio EARS:** Cuando se normalice, la fuente debe ser exclusivamente `data/data.json`; debe recorrer `sesiones` en el orden actual, conservar cada ID entero seguro positivo único y reasignar a cada ID ausente, inválido o duplicado el menor entero seguro positivo libre, sin reordenar ni descartar sesiones. Un ID presente inválido o duplicado es reparable si la sesión conserva válidos sus campos obligatorios. Nunca se modifica el backup durante esta normalización inicial.
- **Criterio EARS:** Cuando se normalice, debe conservar exactamente los mismos valores JSON estructurales de todos los campos raíz, metadata, contadores y sesiones, y solo añadir o reparar `id` y `metadata.nextSessionId`; puede cambiar el orden de claves y la representación textual. La comparación ignora orden de claves, considera `-0` igual a `0` y conserva presencia/ausencia de opcionales. La excepción de IDs inválidos deja de aplicar tras esta normalización.
- **Criterio EARS:** Cuando se normalice, un `id` o `metadata.nextSessionId` ausente, `null`, string, decimal, negativo, cero o cualquier valor que no sea un entero seguro positivo debe repararse; `Infinity` y `NaN` no pueden proceder de JSON, pero cualquier valor no entero seguro positivo que sí proceda de la representación recibida será reparable. `nextSessionId` debe repararse al menor entero seguro positivo estrictamente mayor que el máximo ID usado; si no hay IDs usados, debe ser `1`. La reparación solo es posible si existe un entero seguro positivo libre; si se agota, no se escribe y se responde HTTP 500 con `ID_ALLOCATION_FAILED` y el mensaje exacto `No se pudo asignar un identificador a la sesión.`
- **Criterio EARS:** Cuando se complete la normalización, solo debe modificar estructuralmente los `id`, `metadata.nextSessionId` y, cuando proceda, eliminar un `creado` inválido; debe conservar los demás valores, escribir una vez atómicamente, releer y validar; no debe incrementar `successfulWrites`, activar backup ni modificar el backup. Si el documento leído antes de construir es inválido, responde `DATA_CORRUPT`; si falla escribir, sustituir, releer o validar el principal después de sustituir, responde `WRITE_FAILED`, sin rollback. Nunca se responde `DATA_CORRUPT` después de haber intentado escribir.
- **Criterio EARS:** La alta queda fuera del alcance funcional de esta spec. El mecanismo existente de alta debe consumir `nextSessionId` normalizado de forma serializada; esta spec no cambia su contrato ni añade requisitos funcionales de alta. Editar y borrar nunca reservan IDs.
- **Criterio EARS:** Cuando se opere sobre una sesión, la identificación debe ser exclusivamente por `id`; nunca se debe aproximar por fecha, tema, minutos, posición, huella o valores visibles.

### RF-2. Contratos de API y errores

- **Criterio EARS:** Cuando el cuerpo no sea JSON parseable, o sea JSON válido pero tenga forma incorrecta (type ausente/desconocido, operationId ausente/vacío, payload ausente, campos obligatorios ausentes o extras), debe responder HTTP 400 y `{ok:false,code:'INVALID_SESSION_OPERATION',message:'La operación de sesión no es válida.'}`; la petición se valida sintácticamente antes de entrar en la cola, no se encola, no se normaliza y no muta.
- **Criterio EARS:** Cuando se edite, el JSON lógico debe tener exactamente `{type:'edit-session',operationId:string,payload:{id:number,session:{fecha,tema,minutos}}}`; `session` debe tener exactamente esos tres campos y `payload` exactamente `id` y `session`.
- **Criterio EARS:** Cuando el payload de edición tenga fecha inválida, tema vacío tras `trim` o minutos inválidos, debe responder HTTP 400 y exactamente `{ok:false,code:'INVALID_SESSION_DATA',message:'Los datos de la sesión no son válidos.'}`, sin mutar; la interfaz debe validar los mismos datos antes del envío.
- **Criterio EARS:** Cuando se borre, el JSON lógico debe tener exactamente `{type:'delete-session',operationId:string,payload:{id:number}}`; `payload` no puede tener propiedades extra.
- **Criterio EARS:** Cuando un `id` no cumpla `Number.isSafeInteger(id) && id > 0` —incluidos decimal, 0, negativo, NaN, Infinity, null, string u otro valor fuera de rango— debe responder HTTP 400 con `INVALID_SESSION_OPERATION` y no mutar; cuando sea válido pero no exista exactamente una sesión, debe responder HTTP 404 y `{ok:false,code:'SESSION_NOT_FOUND',message:'La sesión ya no existe.'}`.
- **Criterio EARS:** Cuando el principal falte, debe responder HTTP 500 con `{ok:false,code:'MAIN_DATA_MISSING',message:'No se pueden leer los datos porque no existe el archivo principal.'}`; cuando sea inválido, vacío o corrupto, HTTP 500 con `{ok:false,code:'DATA_CORRUPT',message:'No se pueden leer los datos. Conserva una copia del archivo y corrígelo antes de continuar.'}`; cuando falle una escritura o validación posterior, HTTP 500 con `{ok:false,code:'WRITE_FAILED',message:'No se han podido guardar los datos. Inténtalo de nuevo.'}`.
- **Criterio EARS:** Cuando se reutilice un `operationId` con otra representación lógica, la respuesta debe ser HTTP 409 y exactamente `{ok:false,code:'IDEMPOTENCY_CONFLICT',message:'La operación ya existe con otros datos.'}`.
- **Criterio EARS:** Cuando `operationId` sea válido, debe ser un string cuyo `trim` no sea vacío; para la huella de idempotencia se usará exactamente el string recibido, sin recortarlo ni modificarlo, y el orden de propiedades será irrelevante. La petición válida se encola y la primera operación de la cola ejecuta la normalización pendiente, si procede.
- **Criterio EARS:** Todas las respuestas de error del servidor deben usar `{ok:false,code,message}` y exactamente este contrato: `INVALID_SESSION_OPERATION` (400) — `La operación de sesión no es válida.`; `INVALID_SESSION_DATA` (400) — `Los datos de la sesión no son válidos.`; `SESSION_NOT_FOUND` (404) — `La sesión ya no existe.`; `MAIN_DATA_MISSING` (500) — `No se pueden leer los datos porque no existe el archivo principal.`; `DATA_CORRUPT` (500) — `No se pueden leer los datos. Conserva una copia del archivo y corrígelo antes de continuar.`; `WRITE_FAILED` (500) — `No se han podido guardar los datos. Inténtalo de nuevo.`; `ID_ALLOCATION_FAILED` (500) — `No se pudo asignar un identificador a la sesión.`; `IDEMPOTENCY_CONFLICT` (409) — `La operación ya existe con otros datos.`. El servidor nunca emite `SESSION_INTEGRITY_ERROR`. Todo éxito, incluida una solicitud que normaliza antes de continuar, debe responder HTTP 200 con `{ok:true,document,backupPending}`; la normalización no tiene respuesta separada.
- **Criterio EARS:** Cuando un id válido no exista antes de mutar, `SESSION_NOT_FOUND` será el único error servidor aplicable; el servidor no emitirá `SESSION_INTEGRITY_ERROR`.

### RF-3. Edición y validación

- **Criterio EARS:** Cuando se edite, el sistema debe reemplazar solo `fecha`, `tema` y `minutos` de la sesión identificada y conservar todos los demás valores JSON, incluidos campos desconocidos.
- **Criterio EARS:** Cuando se valide el documento normalizado para una edición o borrado, se conservarán sin reinterpretar el `id`, un `creado` ausente o entero seguro positivo y los campos desconocidos ya persistidos; un `creado` presente con valor inválido se elimina durante la normalización y no bloquea la operación. Solo se validarán y reemplazarán `fecha`, `tema` y `minutos` proporcionados por la edición.
- **Criterio EARS:** Cuando la fecha no sea `AAAA-MM-DD` real en calendario local, el tema sea vacío tras recortar, o minutos no sea entero seguro positivo, debe impedir el envío y mostrar el error junto al campo.
- **Criterio EARS:** Cuando el tema sea válido, debe persistirse recortado; una fecha futura puede guardarse y seguirá excluida de derivados que excluyen futuro.
- **Criterio EARS:** Cuando la operación se confirme, la vista solo debe reconstruirse desde el documento devuelto; ante fallo o incertidumbre debe conservar el estado confirmado anterior.

### RF-4. Borrado

- **Criterio EARS:** Cuando se active borrar, debe mostrarse confirmación explícita de que solo se elimina esa sesión y que no se puede deshacer.
- **Criterio EARS:** Cuando se confirme, debe desaparecer únicamente la sesión identificada, conservarse objetivo, raíz, metadata y las demás sesiones, y aplicarse la política de RF-6.
- **Criterio EARS:** Cuando se cancele, se pulse Escape o falle, no debe modificarse documento, backup, contadores ni vista.
- **Criterio EARS:** Cuando termine el borrado, no debe existir deshacer ni restauración automática desde backup.

### RF-5. Serialización e idempotencia

- **Criterio EARS:** La normalización es una operación interna exclusiva de arranque o primera solicitud, en la misma cola y antes de aceptar edición o borrado. Las solicitudes concurrentes esperan, releen el documento normalizado y reciben el resultado de su propia operación; si normalizar falla, reciben error sin mutar.
- **Criterio EARS:** Cuando la normalización inicial termine correctamente, no debe exponerse como operación API ni incrementar `successfulWrites`; la solicitud que la desencadenó debe continuar y responder con su contrato normal y con el `document` final normalizado.
- **Criterio EARS:** Cuando se repita el mismo `operationId` con la misma representación lógica de las propiedades propias del contrato, debe devolver exactamente la respuesta almacenada originalmente, incluidos `document` y `backupPending`, sin releer ni reaplicar; el orden JSON de propiedades es irrelevante.
- **Criterio EARS:** Cuando cambie cualquier dato lógico del mismo `operationId`, debe rechazar sin mutar.
- **Criterio EARS:** Cuando una edición preceda a un borrado, ambas deben aplicarse; cuando el borrado preceda a la edición, la edición debe devolver `SESSION_NOT_FOUND`.
- **Criterio EARS:** Cuando haya timeout, desconexión o respuesta incierta, no existe respuesta HTTP: el cliente debe mostrar el mensaje existente, no afirmar éxito y no reintentar automáticamente.

### RF-6. Persistencia y backup

- **Criterio EARS:** Cuando se edite o borre correctamente, debe construirse un único documento de datos, incrementar `successfulWrites` una sola vez, escribirlo/validarlo como principal y releerlo antes de responder.
- **Criterio EARS:** Si al comenzar una operación `successfulWrites-backupSuccessfulWrites >= 5`, o el backup falta o está corrupto, y la escritura actual del principal queda confirmada, debe intentarse reconciliar el backup en esa misma operación después del principal. Si no se alcanza el umbral y el backup es válido, no se intenta reconciliación. `backupPending` siempre refleja el estado físico y los contadores; la normalización inicial nunca modifica el backup.
- **Criterio EARS:** Cuando el backup esté ausente, sea nulo o corrupto, nunca debe bloquear una edición o borrado válido ni usarse como fuente; debe operar el principal, responder `backupPending:true` y no producir `DATA_CORRUPT` por ese estado.
- **Criterio EARS:** Si procede backup, se intenta reconciliar desde el principal confirmado, se escribe/valida y después se actualiza la metadata del principal para igualar `backupSuccessfulWrites`; el orden exacto es principal de datos → backup → metadata. La segunda escritura no es otra operación de datos ni incrementa `successfulWrites`. Si la reconciliación falla, se conserva el éxito de los datos principales, `backupPending:true` y un mensaje/aviso; no se cambia el código de éxito ni se restaura el backup.
- **Criterio EARS:** Tras cualquier éxito, `document` es el principal válido de la primera escritura de datos. Si, después de que principal y backup de datos sean válidos, falla únicamente la escritura secundaria que ajusta `backupSuccessfulWrites`, la operación de datos sigue siendo exitosa, devuelve ese principal, `backupPending:true` y reintenta el ajuste en la siguiente operación. Un fallo al escribir, releer o validar el principal después de sustituirlo es `WRITE_FAILED`, sin rollback; no se confunde con el fallo secundario de ajuste.
- **Criterio EARS:** Cuando se normalice inicialmente, el backup debe permanecer intacto, incluso si es válido pero antiguo o carece de IDs.

### RF-7. Orden, paginación e integridad de sesión

- **Criterio EARS:** Cuando se ordenen sesiones, debe aplicarse fecha descendente, `creado` válido descendente, `id` descendente como desempate adicional e índice estable; esta regla reemplaza para sesiones el desempate final de spec 005.
- **Criterio EARS:** Cuando, tras HTTP 200, el cliente no localice en el documento recibido la sesión por su `id`, debe aplicar `SESSION_INTEGRITY_ERROR`, con `No se pudo localizar la sesión actualizada. Recarga la página antes de continuar.`, conservar la vista confirmada y ejecutar una recarga normal de `GET /api/data`, sin usar el `document` de la respuesta ni buscar por fecha, tema, minutos, posición, huella o valores visibles; si recargar falla, conserva la vista anterior y anuncia el error de recarga. El servidor debe responder `SESSION_NOT_FOUND` si el id falta antes de mutar y nunca emite `SESSION_INTEGRITY_ERROR`.
- **Criterio EARS:** Cuando se ordenen sesiones, el orden base será fecha descendente, después `creado` válido descendente, después `id` descendente como nuevo desempate de esta spec y finalmente el índice estable original; no se cambiará ningún otro criterio.
- **Criterio EARS:** Cuando existan sesiones, la paginación será 1-based: `currentPage` estará siempre entre `1` y `totalPages`; solo una lista vacía usará página `0`. Cuando borrar o editar cambie el número de páginas, debe conservarse la página si sigue en rango y ajustarse a la última si procede; una lista vacía usará página `0`.
### RF-8. Derivados actualizados

- **Criterio EARS:** Cuando se confirme cualquier cambio, deben recalcularse desde sesiones la racha, mejor racha, minutos semanales, días del mes, mapa y progreso, respetando fechas locales y exclusión de futuras.

### RF-9. Modal, accesibilidad, teclado y responsive

- **Criterio EARS:** Cuando se edite o confirme un borrado, el modal debe usar `role="dialog"` para edición y `role="alertdialog"` para borrado, `aria-modal="true"`, `aria-labelledby` al título visible y `aria-describedby` a la descripción; el foco inicial va al primer control útil o confirmación.
- **Criterio EARS:** El modal debe mantener focus trap; Escape cancela; cancelación, éxito o error devuelve el foco al botón origen. Una región `aria-live` anuncia procesamiento y errores, y los controles quedan bloqueados durante la petición.
- **Criterio EARS:** La edición debe usar `#dialogo-edicion`, `role="dialog"`, `aria-modal="true"`, `aria-labelledby` y `aria-describedby` apuntando a título y descripción visibles, campos en orden fecha → tema → minutos, botones `Guardar cambios`/`Cancelar`, foco inicial en fecha, focus trap y Escape/cancelación devolviendo el foco al botón `Editar sesión` con su `id`. Fecha y tema deben insertarse como `textContent`/valor, nunca como HTML.
- **Criterio EARS:** Cuando se confirme borrado individual, debe reutilizar el existente `#dialogo-borrado`, con `role="alertdialog"`, `aria-modal="true"`, título `Borrar sesión`, descripción `¿Quieres borrar la sesión del <fecha>, «<tema>», de <minutos> minutos? Esta acción no se puede deshacer.`, botones `Borrar sesión`/`Cancelar`, foco inicial en la confirmación, focus trap, Escape/cancelación y bloqueo equivalentes; nunca texto de borrar todas. Fecha y tema deben insertarse como `textContent`/valor, nunca como HTML.
- **Criterio EARS:** Cuando se muestre fecha en la descripción individual, debe usar `es-ES`, componentes locales, mes minúsculo y formato `D de mes de AAAA`, sin UTC; edición muestra input date sin texto formateado.
- **Criterio EARS:** Cuando se muestre fecha en la descripción individual, debe construirse con componentes locales y un array fijo de meses `['enero','febrero','marzo','abril','mayo','junio','julio','agosto','septiembre','octubre','noviembre','diciembre']`, en formato `D de mes de AAAA`, sin UTC.
- **Criterio EARS:** Cuando, después de HTTP 200, el cliente no pueda superar el guard mínimo de transporte/render (`result.document` objeto, `sesiones` array y `metadata` objeto) o no pueda localizar en él la sesión objetivo, debe aplicar el único estado/tratamiento de cliente `SESSION_INTEGRITY_ERROR` con el mensaje `No se pudo localizar la sesión actualizada. Recarga la página antes de continuar.`; esta condición tiene precedencia sobre cualquier otro tratamiento de éxito: no se afirma éxito, se conserva la vista anterior, se cierra y desbloquea el modal, se devuelve el foco al origen, se anuncia el mensaje y se ejecuta `GET /api/data`. Si ese GET falla, se conserva la vista anterior y se anuncia el error de recarga. El cliente no clasifica corrupción ni normaliza; el servidor nunca emite este código.
- **Criterio EARS:** Cuando se muestre a 375 px o se use teclado, lector de pantalla, tacto o activación programática, no debe haber overflow y el foco debe ser comprensible.

### RF-10. Documentación y flujo de trabajo

- **Criterio EARS:** Al iniciar el trabajo deben leerse AGENTS.md, `docs/constitution.md`, MEMORY.md, README.md, las specs 003/005/006, el código afectado y los tests necesarios; README.md puede leerse durante todo el flujo, pero solo se modifica o revisa públicamente en T10. MEMORY.md se actualiza al terminar cada tarea conforme a AGENTS.md.
- **Criterio EARS:** Cada tarea empieza solo con la anterior verde; si `node --test` falla al terminar cualquier tarea, se detiene el flujo. Tests-first puede producir tests rojos temporalmente, pero no se termina ni se avanza hasta que vuelvan verdes.

## Casos límite

Debe cubrirse clasificación NORMALIZABLE/DATA_CORRUPT con precedencia explícita y autoridad exclusiva del servidor/repositorio: forma y campos obligatorios válidos más IDs reparables son NORMALIZABLE; cualquier fallo obligatorio es DATA_CORRUPT; contrato único normalizado de sesión y metadata, `migration` intacta, `creado` opcional y `nextSessionId` estrictamente mayor; normalización sin localStorage ni cambios a `sources`, `ignoredSources`, `status` o `completedAt`; `SESSION_NOT_FOUND` como único error servidor para id ausente y ningún `SESSION_INTEGRITY_ERROR` servidor; el cliente solo valida formularios y muestra respuestas; la ruta cliente única de integridad tras HTTP 200 conserva vista, cierra/desbloquea modal, anuncia y ejecuta `GET /api/data`; además, raíz no objeto, campos raíz ausentes, objetivo inválido, migration inválida, contadores inválidos, campos obligatorios de sesión inválidos, desconocidos conservados, IDs reparables, backup intacto, persistencia, idempotencia, incertidumbre, fechas locales, modales, foco, focus trap, Escape, bloqueo y 375 px.

## Decisiones cerradas

- `documento-v1-legado` solo es válido para lectura/migración durante la transición; editar/borrar exige `documento-v1-normalizado`.
- La normalización solo añade/repara IDs y `metadata.nextSessionId`, escribe una vez atómicamente, relee/valida, no cuenta ni activa backup y deja el backup intacto.
- `nextSessionId` no es contador de escrituras: si falta o es inválido se repara durante normalización cuando el documento y los campos obligatorios son válidos; es el menor entero seguro positivo estrictamente mayor que el máximo usado, o 1 sin IDs. Cada alta lo consume y lo incrementa sin reutilización; `successfulWrites` y `backupSuccessfulWrites` inválidos producen `DATA_CORRUPT`.
- La política de backup es una escritura principal por edición/borrado, con copia del principal confirmado y segunda escritura lógica controlada; fallo de esta deja principal válido y `backupPending:true`.
- La representación lógica propia del contrato, no el orden textual JSON, define la idempotencia.
- La spec 006 sustituye el desempate de spec 005 para sesiones; README puede leerse durante todo el flujo, pero solo se modifica o revisa públicamente en T10, tras implementación y verificación, y plan/tasks deben reflejarlo.
